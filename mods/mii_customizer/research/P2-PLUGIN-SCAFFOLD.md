### 2.1 Dependency: exactly one, pinned

```
skyline 0.6.0
git  https://github.com/ultimate-research/skyline-rs
rev  6b52d321275639f26c2371d8142550ba0013a5e4
```

This is **the exact revision the reference plugin's `Cargo.lock` resolves for `skyline`**
(`Cargo.lock:409`). Resolved graph (`plugin/Cargo.lock`):

| crate | version | source |
|---|---|---|
| skyline | 0.6.0 | git skyline-rs `?rev=6b52d32…#6b52d32…` |
| skyline_macro | 0.2.1 | same git source, path dep inside the skyline repo |
| libc-nnsdk | 0.5.0 | crates.io |
| nnsdk | 0.6.1 | crates.io |
| lazy_static, proc-macro2, quote, syn, unicode-ident | - | crates.io (proc-macro support) |

**No dependency was added beyond `skyline`.** Nothing had to be justified away: the build
worked first try with this graph.

Why the reference plugin could not use `rev` and this one can: the reference crate also
depends on `skyline_smash`, `smash_script` and `smashline`, each of which pulls `skyline`
through the *bare* git URL. Cargo compares git sources by URL alone, so `rev` there puts two
copies of `skyline` in the graph (measured there as 327 E0308 errors plus an ambiguous
`FighterEntry`). With `skyline` as the only git dependency there is nothing to collide with,
and the pin is honest rather than lockfile-implied. Note the divergence: the reference
crate's graph also resolves `nnsdk 0.6.2` from git `nnsdk-rs#d23f131…` via its other
dependencies; this graph takes `nnsdk 0.6.1` from crates.io. Both are what their own lockfile
resolves for the `skyline` they compile against; neither crate calls any `nnsdk` function.

### 2.2 The entry point

   (`skyline::logging`'s `#[macro_export]`ed `println`, in

No hook, no `skyline::patching`, no `skyline::hooks`, no `skyline::nro`, no game function, no

### 3.4 Required checks, individually

**(a) NRO exists and starts with the expected magic.**

The NRO header is: u32 branch instruction at `0x00`, u32 mod_offset at `0x04`, then the
4-byte ASCII magic `NRO0` at **offset `0x10`**. That is the offset this format uses; I read it
directly:

```
00000000: 0000 0000 1850 0000 0000 0000 0000 0000  .....P..........
00000010: 4e52 4f30 0000 0000 0090 0000 0000 0000  NRO0........
```

- `0x00`: `00 00 00 00` - branch instruction
- `0x04`: `18 50 00 00` - mod_offset = `0x5018` = 20504
- **`0x10`: `4e 52 4f 30` = ASCII `NRO0`** - PASS
- at `mod_offset` `0x5018`: `4d 4f 44 30` = ASCII `MOD0` - the asset section magic, also PASS
- `xxd` dump saved at `evidence/P2-PLUGIN-SCAFFOLD/nro_header.txt`; exit 0.

**(b) The binary contains the version string and the log path string.** `grep -abo`, exit 0:

## 6. Limits and unresolved questions

1. **No runtime evidence of any kind.** The plugin has never been loaded by Skyline, never
   run in the game, never seen on a console or emulator. Whether it loads at all on 13.0.4,
   whether `sd:/ultimate/` is writable at plugin-load time, and whether the line appears in
   either log are all **unverified**. Tier D until someone installs it.
2. **The plugin name in the NRO is `mii_customizer`** (from `#[skyline::main]`), so a card
   filename and load order are a coordinator decision, not made here.
3. **`nnsdk` resolves differently** from the reference crate's graph (`0.6.1` from crates.io
   vs `0.6.2` from git). Harmless for a log-only plugin - no `nnsdk` symbol is called - but
   it is a real divergence if this crate ever grows into one that does.
4. **No `paths.toml`** exists in this mod yet, so `build-plugin.sh` resolves everything from
   its own location. No absolute machine path is hardcoded in any file.
5. **`builds/.cache/` is ~185 MB** (std compiled for `aarch64-skyline-switch`). Disk is
   scarce per the reference mod's rules; prune when this stops being useful.
6. **`cargo update` must not be run** on this crate - it would move off `6b52d32`, the
   revision the lab's other tooling was verified against. `Cargo.lock` is the backstop.
7. `--offline` works only because every pinned crate is already in this machine's cargo
   cache. A new pin needs one online run first (`build-plugin.sh --online`).
